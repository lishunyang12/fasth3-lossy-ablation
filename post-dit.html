The full post-denoising optimization history behind FastH3: accelerate the full video VAE, preserve finalized frames through asynchronous transfer, and overlap CPU media production with GPU decoding.

01 / EXECUTION MODEL

A pipelined post-DiT system

Each decoded temporal window is spatially tiled across eight GPUs. Rank zero gathers and blends those tiles, then emits only temporally finalized frames. Video transfer and CPU encoding can begin while later VAE windows are still being decoded. Audio follows a separate branch and joins at muxing.

01 · GPU × 8Full video VAE

Paired temporal windows, mixed B4/B3 tile batches, exact pointwise operators and NVFP4 linear layers.

02 · NCCL → RANK 0Gather + blend

FP32 tile payloads. Spatial blending first; five-frame temporal overlap retained until finalized.

03 · GPU COPY STREAMFused RGB + D2H

Inverse normalization, crop, layout and uint8 conversion. Asynchronous copy into two pinned host buffers.

04 · CPU MEDIA WORKERx264 + MP4

RGB-to-YUV420 conversion, ordered video encoding, video flush, AAC packet mux and container close.

Parallel audio branch: audio latent → unchanged audio VAE on an auxiliary CUDA stream → pinned waveform D2H → background AAC encoding → retained packets with original timestamps → final MP4 mux.

Figure 1. Dependency graph, not a timing diagram. Separate streams and threads permit overlap; they do not guarantee that all work is hidden. The API still returns a complete MP4, so early encoded packets are not yet client-visible video.

Response ready = completion of both media branches + remaining flush, mux and response work

For the current five-second request, seven temporal windows produce 7 × 17 + 5 = 124 frames. The 28 spatial tiles per window yield 196 real tile outputs across eight ranks. The scheduler pads collective buffers where needed, but never decodes or presents padding tiles. The five-frame overlap is an internal VAE reconstruction rule; it is distinct from inter-clip motion context in a livestream.

02 / DECODER COMPUTE

Remove repeated work before lowering precision

The exact-op installer combines Q/K RMS normalization with RoPE, uses fused SiLU-and-multiply for the feed-forward activation, and combines scaled residual operations while preserving the qualified rounding behavior. It also persists decoder linear weights in FP16 on the unquantized path, matching the casts already performed by FP16 autocast. This avoids repeatedly rebuilding equivalent weight casts. The encoder remains FP32.

That FP16 residency change is superseded by resident packed weights when NVFP4 is enabled. The exact operators remain active. Native blocks expose fused QKV, output, FF input and FF output projections: four linears per block, or 144 total. The stock FastVideo representation instead exposes separate Q/K/V projections and has 216 linears for the equivalent 36-block decoder.

Batch tiles without changing the assembly contract

The paired scheduler distributes two temporal windows together. Mixed batching groups up to four independent tile decodes while preserving each tile's position in the gather schedule. Attention output projection remains at its original B1 shape and stride. On the current request, every rank makes seven batched decoder calls instead of separately invoking the decoder for its 24 or 25 tiles; output projections still run per tile. Batching is an execution change, not a blanket proof of bitwise equivalence for arbitrary GEMM shapes.

No isolated full-request speedup for pairing or B4 batching is assigned here. Their inclusion is verified by source and dispatch counters; the measured decoder A/B above has its own explicitly stated scope.

03 / LOSSY DECODER ACCELERATION

NVFP4 is a measured precision tradeoff

The native NVFP4 path replaces only the 144 transformer-block linears. Original FP32 weights are quantized once at installation and remain packed on the GPU. Each invocation dynamically quantizes its FP16 activations, executes cuBLASLt block-scaled GEMM, and returns FP16. Activation quantization and scale reduction remain in the timed decode path.

MXFP8 · historical option

E4M3 payload, E8M0 scales per 32 elements; FP16 activation/output boundaries. Weight quantization occurs once, activation quantization per call.

LOSSY · CURRENTLY DISABLED

NVFP4 · current option

Packed E2M1 payload, E4M3 block scales per 16 elements, FP32 tensor scales; FP16 activation/output boundaries. Convolutions and all other VAE operations are not converted wholesale to FP4.

04 / COMMUNICATION AND AUDIO OVERLAP

Move work off the serial tail

VAE gather uses a dedicated NCCL stream and FP32 payloads. Early gather sends the first four decoded tiles while the remaining three are computed; rank-zero assembly can overlap the next decode round. CUDA events and stream ownership retain buffers until the consuming work finishes. This VAE gather path is separate from the custom RDMA used inside DiT.

The audio VAE starts on an auxiliary stream before video decoding. After the waveform is ready, a separate stream transfers it to pinned CPU memory; a background thread encodes AAC. Finalization reuses the encoded packets, preserving codec settings, extradata, timestamps and mux order. This reschedules audio processing; it does not replace the audio decoder or change its precision.

Cached normalization constants remove per-chunk constant transfers and the repeated host-visible standard-deviation check. Its initial implementation retained the original FP32 subtract/divide operations. The current fused RGB path incorporates the same cached-constant semantics, so these savings must not be counted a second time.

05 / GPU ASSEMBLY AND POSTPROCESSING

Fuse the output while preserving rounding

Spatial and temporal blend

Cache the original Torch-generated overlap weights, then combine two multiplies, the sum and unaffected-region copying in one kernel. Preserve vertical-before-horizontal assembly and the original separate FP32 rounding; avoid contracting arithmetic into FMA.

BYTE-EXACT ON QUALIFIED INPUTS

Finalized frames to RGB bytes

Fuse inverse normalization, crop, BCTHW-to-THWC layout, clamp, scaling, round-to-nearest-even and uint8 conversion. Keep the original subtract/divide formulation rather than replacing it with algebraically equivalent multiply-add.

BYTE-EXACT ON QUALIFIED INPUTS

The five-frame overlap stays in floating point until temporal blending is finished. Only finalized pixels are converted to uint8. Quantizing the overlap earlier would introduce an additional numerical change and is not part of this path.

06 / D2H, CPU ENCODING AND MUX

Transfer finalized bytes; consume them in order

The chunked output path avoids assembling and transporting a full-resolution floating-point video on rank zero. GPU conversion produces RGB24 bytes before D2H. At the current 1344 × 768 resolution, 124 frames require 366.19 MiB of RGB uint8 payload, compared with 1,464.75 MiB for the same RGB pixels in FP32: four times fewer transfer bytes by dtype alone. This byte-count ratio is not a measured fourfold latency gain.

An earlier single-output fast path also removed a redundant full-clip torch.cat: one generated sample can be returned directly, while true multi-output requests retain concatenation. The chunked-MP4 route goes further by never constructing that full decoded output tensor. These are related stages in the output architecture, not two independently measured savings to add together.

More pinned slots, smaller D2H chunks and GPU YUV conversion remain unadopted ideas. Current logs show no producer backpressure at millisecond precision, and the historical D2H copy cost is small. CPU colorspace-thread experiments produced only small, overlapping replay-tail differences; neither those changes nor a hardware encoder are counted as deployed improvements.

Remaining work, ordered by evidence

First, qualify the CPU buffer-view candidate inside the complete five-second path, holding encoder parameters fixed to isolate the copy removal. Then evaluate FRAME/CFR settings separately, including buffering, video quality, timestamps and the final response tail. The CPU replay suggests an opportunity; it does not prove a live gain.

For larger decode gains, investigate the actual VAE compute path: activation quantization, scale reductions, activation/normalization boundaries, and B4/B3 GEMM shapes. The historical profile identifies work to study, but none of its kernel totals is a guaranteed saving. More D2H slots are lower priority until measured backpressure or transfer saturation appears.

Long-video identity drift, audio articulation and livestream viewer latency require separate evaluations. Decoder precision metrics, byte-exact output transforms and faster MP4 production do not by themselves establish those product-level properties. Twitch buffering, network transport and the interaction harness are outside this report's measured boundary.

Measurement and reproducibility notes

Unprofiled complete-request measurements exclude model loading, compilation, warmup and post-response verification. GPU campaigns were admitted only after their recorded run checks; clocks were not locked and most configurations ran sequentially. Three or five samples are descriptive, not a p99 service guarantee. Single-sample quantization timing is explicitly identified. CPU tuning did not reserve the entire host. Exactness claims apply to the compared tensors or files in the stated tests, not arbitrary hardware and inputs.

The evidence JSON includes original timing samples, seven-prompt quality scores, sanitized profiler timestamps, current execution counters and hashes of the relevant source files. Historical 704p and current 768p results stay separate. All existing media is reused without re-encoding.
